# CITIC 数据检查记录

更新：2026-11-06｜状态：首组解码及投影计算已检查，时间对齐与标定精度待验证

## 来源与体积

- [数据集仓库](https://github.com/GTEC-UDC/citic-mtmc-dataset)及其 [Zenodo 版本归档](https://zenodo.org/records/17512043)。归档文件 763,352,844 字节，约 728 MiB；Zenodo 列出的完整包 MD5 为 `11006494bb4c7580e57b0b65d09fb139`。按 HTTP Range 提取的文件应以 ZIP CRC 验证，不能声称完整包 MD5 已验证。
- 压缩包目录包含三组 capture，每组 HallSeg、HallWide、PC、PF、Showroom 五路视频。已按范围下载并提取 capture1 的 HallSeg（17,351,825 字节）和 HallWide（44,694,864 字节），两文件的 ZIP CRC 校验通过。二者均 172.72 秒、标称 25 fps，分辨率分别为 720×576 和 1280×720；从本机 AVFoundation 读取。
- 已用 OpenCV 从两路视频各解码 0、5、10、20、30 秒帧，得到对照图 `data/processed/citic_inspection/contact-sheet.jpg`；画面可以观察到人物，但这些稀疏帧无法证明同一人同时出现或两路视频同步。0–30 秒暂作解码窗口，不视为已验证的跨镜头匹配样本。
- 下载文件保存在本地忽略目录 `data/raw/`，不提交仓库；数据 CC BY-NC-SA 4.0，仓库提供的代码为 MIT。内部研究用途已确认，实际使用仍遵循数据条款。

## 空间与同步

- 项目文档说明大厅有两台摄像头、两个通道和一个展示厅各有一台；不能把展示厅的单视角称为多视角重叠。
- `NodeHallSeg.json` 提供单应矩阵；`NodeHallWide.json` 提供内参和外参矩阵及地面可见区域。两者投影实现不同，需验证坐标方向和实际误差；两份可见区域在大厅有几何重合，实际画面覆盖仍需检查。
- 已将 HallSeg 单应矩阵与 HallWide 的 `K[r1 r2 t]` 地面矩阵转换为图像到地面的映射；各选 3 个图像点，投影及逆投影的最大数值回环误差小于 0.000001 像素。这仅验证矩阵可逆及计算自洽，不证明真实定位精度、坐标约定或时间同步。
- `room_map.json` 包含区域和门的位置，以及平面图比例（25 像素/米）；先将大厅两个区域作为空间基线，后续再接通道和展示厅。
- 录像已处理为固定 25 fps，源摄像头的实际帧率不同，不能因此推断有效画面信息均为 25 fps。`timesyncs.csv` 用于手机与服务器时间偏差处理，不应直接当作摄像头之间的偏移。生成脚本给出 capture1 参考视频起始时刻，但各视频首帧同步情况仍待核验。

## 参考数据限制

位置参考由参与者经过离散路点的时间和坐标线性插值生成；不是连续精确真值。`capture1_gt.mot.txt` 样本中的框坐标为 -1，不能直接作为人员检测框真值；脚本还排除了一名参与者。因此需先检查覆盖人数、坐标/帧对齐和插值误差，不能将所有画面中的人都当作有真值。

## 本机环境

- Apple M1 Pro，16 GB 内存，优先本机短片段离线处理。
- 系统 `/usr/bin/python3` 3.9.6 可启动；当前默认 nanobrew Python 3.14 和 ffprobe 启动时报动态库缺失。尚未判断是否影响其他隔离环境，后续应选择可复现的隔离运行时并再次验证。
- 用户要求使用 uv 管理 Python 环境；已用 uv 0.6.4 创建 CPython 3.12.9 环境。接入 YOLO 后 NumPy 调整为 1.26.4、OpenCV 4.11.0.86，并重新锁定。`uv run --locked python scripts/inspect_citic.py` 已完成两路抽帧和矩阵计算；模型基线见 [结果](07-baseline-results.md)。
- 用户有双 5060 Ti、48 GB 内存 PC；只在本机实际遇到必要瓶颈时考虑使用。
